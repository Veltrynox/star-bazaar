Game concept

Ships fly automated routes between worlds; the player chooses what to invest in: routes, ships, workshops, permits for new solar systems and skills. Worlds the player keeps supplied grow through Prosperity tiers.

The goal is to found the Star Bazaar in a system's Space Storage, build it stage by stage and open it with a final charter delivery before the term ends. Three trading houses act as “weather” (floods, shortages, congestion), never as rivals.

How to play in two minutes

  1. Open star-bazaar-beta.vercel.app in a desktop browser (Chrome, Edge, Firefox or Safari with WebGL 2). The first load downloads about 90 MB and takes 10 to 30 seconds.
  2. On the main menu click New Game. Type a company name (or press Random), pick one of the four CEO portraits and press Start.
  3. Read the short preface. The game starts paused and a guided tutorial walks you through the first steps: pick a world, place a Buy order, Send to… another world, run a cycle.
  4. Controls are mouse only. P pauses; the speed buttons (1x, 2x, 6x, 12x) set how fast cycles run. Saves are kept in your browser.

The web build is a Godot 4.7.2 HTML5 export (no threads, so it needs no special server headers). Its source is the web-build branch, folder web/.

Pipeline & Engine Integration

A team of Claude Code role agents builds the game. Every agent writes to a fixed file format that the engine or a build script reads directly, so no output is reformatted by hand.

Sonnet agent Haiku agent Owner scheduling / control file handoff feedback → new task

Automated flow

The agents are defined in .claude/agents/*.md and work is queued as tasks in schedule.json. Agents hand work to each other through files (handoffs/, blackboard.md, design/proposals/), and their output lands in the engine through fixed formats:

Story & UI textThe story-designer writes plain Markdown blocks in story/*.md (ID | max length | place, then the text). tools/build_story.py is the only writer of the three generated JSON files; it checks ids and length limits and stamps each file with a generated marker. The game loads them at runtime, so a new event shows up with no code change.
TranslationHaiku agents write story/ru/*.json by hand under story/ru/GLOSSARY.md; the same build step merges them into data/story_text_ru.json for the in-game language switch.
Data & codeThe economy-designer edits data/*.json; game code reads every number from these files. Programmer agents write GDScript in game/. A commit hook (tools/gdd_sync.py) blocks any commit that changes game/, data/ or story/ without updating gdd.md.
Art & audioTool scripts write engine-ready files: texture atlases (tools/make_*_atlas.gd, headless Godot), planet textures, icons and UI (tools/make_icons.py, tools/make_ui.py) and the space ambience (tools/make_ambient.py).
Unattended runs & releasetools/orchestrator.py run starts one headless claude -p "/overnight-worker <id>" per ready task in its own git worktree, then rebases, runs the tests and fast-forward merges each finished task; conflicts go to a merge-resolver agent. A headless Godot export builds the web version and vercel --prod publishes it.

Pipeline Audit

Everything listed here ships in the playable build. Counts are taken from the repository on 25 November 2026.

What the pipeline produced

Text
3,172 English and 2,961 Russian text ids: events, choices, gig stories, endings, skills, tutorial, tips and every UI label
Narrative
25 base events, 63 chain events and 40 chain steps, 7 gigs (story missions), a 70-node skill tree and end-of-run scenes told as a story
Economy
22 goods, 5 workshops and the balance tables for prices, upkeep, Prosperity growth and the Star Bazaar stage bills
Game code
89 GDScript files, about 32,000 lines: trading loop, automated routes, Prosperity, the Star Bazaar, events, tutorial, UI panels, planet shaders and FX, juice animations
Generated assets
Planet banner, portrait and skill-icon atlases, UI icons, the space ambience track
Process
264 scheduled tasks (261 done), 1,014 commits; 84 tasks ran through the unattended orchestrator (73 merged automatically, 11 blocked for a human)

Manual steps that remain

  1. Owner approval of designs. By project rule, design and proposal tasks produce a proposal only; the owner approves it before any agent builds it.
  2. Visual review. The owner looks at every visual result in the running game. Agents only take one screenshot to catch objective breakage (blank, clipped or overlapping text).
  3. QA and balance runs are started by hand. The QA bots (qa/check) and economy retunes are started only by the owner.
  4. Blocked merges. 11 of 84 orchestrator tasks stopped on a test failure or a rebase conflict the resolver could not settle.
  5. Release. Commit, push, web export and the Vercel deploy are still started by hand.

What it would take to remove them

Approvals & reviewA scored acceptance gate: an evaluator agent with a written rubric, plus screenshot diffs against approved reference images. The owner samples results instead of reviewing each one.
QA & balanceRun qa/check in CI on every merge to main with fixed thresholds (win time, dominant strategy, softlocks); a breach opens a task for the economy designer.
Blocked mergesSmaller tasks with non-overlapping touches globs, and a retry that rebuilds the task on fresh main before handing it to a human.
ReleaseA CI job (GitHub Actions with headless Godot) that exports the web build and deploys it to Vercel on every push to main.

Architectural Reflection

One decision I would make differently, backed by the measured cost split of the run.

Current decision to change

Most work ran from one long-lived interactive main session on a large model. That session read files, briefed role agents, checked their output and committed. Its context grew for hours and was written into the prompt cache again and again.

Interactive sessions + their agents
$799
95% of the total
Orchestrator workers
$41.78
84 tasks
Cost per orchestrated task
≈ $0.50
fresh, short-lived worker

Specific alternative

Make the orchestrator the default path, not the exception.

  1. schedule.json becomes the only way work enters the pipeline.
  2. tools/orchestrator.py starts a fresh, short-lived headless worker per task on Sonnet (Haiku for translation and text checks), given only that task's brief and the files its touches globs name.
  3. The interactive session is kept for owner conversations and for writing task briefs; it never does the build work itself.
  4. Each worker ends with a structured result line and a handoff file, so no session needs a growing context.

Solo / small-team sustainability

Yes, on a subscription. A $200 flat fee covered work worth $841 at API rates: about 260 finished tasks and a playable game in a month.

On pay-as-you-go API billing, about $800 a month is still affordable for a small team, but 95% of it went to the expensive interactive style of work. The orchestrator path cost about $0.50 per task and the Haiku translation path a few cents per batch, so moving build work to short headless workers would bring the API cost down to the low hundreds per month.
